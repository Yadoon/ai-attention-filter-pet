# 设计文档：跨平台 AI 内容过滤与注意力伴生宠物（Web 端）

> **文档状态**：Draft v2.0（已融合边界审查与架构重构）  
> **目标读者**：核心开发、前端/算法协作者  
> **一句话结论**：我们做一个**纯本地运行的浏览器扩展（MVP 零后端安装）**，用“投喂电子宠物”的交互收集你的审美偏好，在 B 站、小红书、抖音网页版的信息流里，结合 **BGM/元数据规则 + 本地多模态向量（WebGPU/WASM）+ 正负样本纠偏**，实时拦截 AI 批量水货与同质化洗稿内容。

---

## 1. 背景与问题

现在打开视频和图文平台，推荐流里充斥着大量 AI 批量生产的“低密度水货”：同套路标题党、换皮洗稿文案、固定罐头 BGM 配悬疑解说、以及高度同质化的跟风热点。

平台原生的“不感兴趣”按钮几乎无效——你点十次，明天照样推换了个马甲的同类账号。市面上现有的屏蔽插件要么只靠手写关键词/正则（维护成本高，普通人懒得配），要么直接把整个推荐流全藏起来（只适合学习防分心，不适合“想正常刷内容，但只想看高质量内容”的人）。

我们需要一个站在用户这一侧的**客户端本地过滤引擎**：用极低门槛的交互（给宠物喂垃圾）持续学习你的偏好，在内容进入视野前把它悄无声息地拦下来。

## 2. 目标与非目标（Goals & Non-Goals）

### 2.1 本期目标（Goals）
1. **开箱即用，零本地后端依赖**：MVP 阶段采用纯浏览器扩展架构（MV3 + Offscreen Document + WebGPU/WASM），用户装完插件即可运行，无需单独安装 Python 或 Docker。
2. **多平台统一抽象，B 站先行**：先在 B 站网页版跑通完整闭环，再以独立适配器扩展至小红书和抖音网页版。
3. **有效拦截且可控误杀**：
   - 信息流列表页单批（10～20 张卡片）本地判定耗时 **P95 < 150ms**（启用 WebGPU 时）。
   - 任何拦截均可逆，支持一键“吐出”纠偏，且纠偏后同类优质内容不再被同一负样本误杀。
4. **100% 本地数据主权**：所有浏览特征、向量库、黑/白名单全部保存在用户本地（`IndexedDB`），零隐私上报。

### 2.2 本期非目标（Non-Goals）
为了避免范围失控，MVP 和 V1 阶段**明确不做**以下内容：
* **不做手机 App 端拦截**：移动端无标准 DOM 注入通道，强行做无障碍/代理抓包成本极高且风控风险大。
* **不在列表页主动请求详情接口或全量拉取视频流**：列表页严格遵守**零额外网络请求**原则，不批量爬 CC 字幕、不批量拉视频抽帧，避免触发平台 412/验证码风控。
* **不做“绝对准确的 AI 生成检测器”**：我们不承诺在学术意义上 100% 识别某段文字是不是 LLM 写的；我们只负责拦截**你不喜欢看、信息密度低、或高度重复**的内容。
* **不做强依赖云端账号的商业化后台**：MVP 阶段不建用户账户体系和云端推理集群。

## 3. 核心架构与数据流

我们采用 **“WXT 现代扩展骨架 + Offscreen 本地推理引擎 + 站点适配器（Adapter）”** 的三层解耦架构。数据获取以**被动拦截页面原生 API 响应为主、DOM 映射为辅**，避免纯靠脆弱的 CSS 选择器刮取数据。

```text
+-----------------------------------------------------------------------+
|  目标网页 (bilibili.com / xiaohongshu.com / douyin.com)                |
|  +---------------------------+      +------------------------------+  |
|  | Main World Hook (轻量注入) |      | Content Script (站点适配器)   |  |
|  | 被动拦截 Feed XHR/Fetch    | ---> | 映射 DOM 卡片 / 渲染遮罩与宠物 |  |
|  +---------------------------+      +--------------+---------------+  |
+----------------------------------------------------|------------------+
                                                     | Batch 消息 (10~20条)
                                                     v
+-----------------------------------------------------------------------+
|  Background Service Worker (路由调度 / 缓存 / 跨标签页状态同步)        |
+------------------------------------+----------------------------------+
                                     | 本地模型推理请求
                                     v
+-----------------------------------------------------------------------+
|  Offscreen Document (本地 AI 推理与存储引擎，100% 浏览器端离线运行)     |
|  +-------------------+  +----------------------+  +----------------+  |
|  | L1 确定性与元数据  |  | L2 多模态向量检索     |  | L3 按需深度评估 |  |
|  | 作者/关键词/BGM ID |->| 文本+封面 (WebGPU)   |->| 详情页/播放态   |  |
|  | (O(1), < 1ms)     |  | 负样本 vs 正样本白库  |  | (音频/长文熵)  |  |
|  +-------------------+  +----------------------+  +----------------+  |
|                            ^                                          |
|                            | 读写持久化                                |
|                 [ IndexedDB (向量矩阵 + 规则 + 统计) ]                 |
+-----------------------------------------------------------------------+
```

### 3.1 统一内容数据契约（Normalized Item Schema）
不同站点的数据结构差异很大，所有适配器必须把原始 Feed 数据清洗成以下统一 Schema，再交给过滤引擎：

```json
{
  "platform": "bilibili | xiaohongshu | douyin",
  "item_id": "BV1xx411c7mD",
  "media_type": "video | short_video | image_text",
  "author_id": "12345678",
  "author_name": "示例UP主",
  "title": "内容标题",
  "snippet": "正文摘要或简介（列表页可为空）",
  "tags": ["AI", "科技"],
  "cover_url": "https://...",
  "bgm": {
    "music_id": "73219847123",
    "music_title": "悬疑解说通用配乐"
  },
  "duration_sec": 185,
  "metrics": {
    "views": 12000,
    "likes": 85,
    "danmaku": 3
  },
  "fetched_at": 1795651200
}
```
> **说明**：`bgm` 和 `metrics` 为可选字段。抖音/小红书原生响应自带 `music_id`，B 站列表页则重点利用 `duration_sec` 和 `metrics`（如播放/点赞异常比）辅助打分。

### 3.2 三级过滤漏斗设计（避免误杀的核心机制）

我们把过滤拆成由快到慢的三层，并**严格区分“主题相似”与“低质风格”**。

#### L1：毫秒级确定性规则与元数据加权（零模型算力，< 1ms）
* **显式黑/白名单**：你手动拉黑的作者、关键词、正则直接拦截；手动加入白名单的关注 UP 主直接放行（跳过后续所有层）。
* **罐头 BGM 嫌疑加权（高性价比特征）**：营销号和 AI 矩阵号高度复用那几十首配乐。当同一个 `music_id` 在你“投喂”的垃圾内容里出现 ≥ 2 次时，系统自动把它标为高危配乐，后续命中该 BGM 的视频直接叠加嫌疑分（如 +40 分），无需跑音频模型就能拦住大片套路号。
* **高频 AI 模板句式**：匹配典型洗稿话术（如“震惊！99%的人不知道”“在这个……的时代”），作为加权特征而非单独一票否决。

#### L2：本地多模态向量检索与“正负样本边界”（WebGPU / WASM）
很多同类方案直接用“标题余弦相似度 > 0.82 就拦截”，这在实际使用中会产生严重误杀。
> **反例**：你投喂了一条 AI 洗稿视频《震惊！GPT-5 正式发布，99%的人不知道》，标题向量记住的是“GPT-5 发布”这个主题。如果只看语义相似度，下一秒 B 站硬核 UP 主发的《GPT-5 架构实测与源码解析》也会因为主题相似被一并误杀。

为此，L2 做三项关键设计：
1. **文本 + 封面双模态互补（Phase 2 补齐封面）**：
   - 文本侧运行量化版 `bge-small-zh-v1.5`（ONNX），抓主题重复和洗稿换皮。
   - 视觉侧运行轻量 `MobileCLIP`（ONNX），对卡片封面图做视觉向量化，抓“红黄粗体大字报 / AI 油腻封面 / 固定营销模板”。
   - 同样讲 GPT-5，硬核极客架构图封面和 AI 震惊体大字报封面的视觉向量距离很远，能有效区分质量。
2. **负样本库（Negative Bank）与正样本白库（Positive Anchor）对抗打分**：
   - 你点击“投喂” → 写入负样本库。
   - 你点击“吐出（误杀纠正）” → **不是盲目删掉历史黑名单**，而是把这条被误杀的内容写入**正样本白库**，同时记录并降低触发本次误杀的那条历史负样本的权重。
   - 判定公式采用边界差值：只有当 `Score_neg(x) - α * Score_pos(x) > Threshold` 时才触发拦截。越用越准，不会出现“一误杀就废掉旧规则”的情况。
3. **24 小时“有效已读”滑窗去重**：
   - 严格区分**曝光**与**有效已读**：只有你实际点击进入、或在视口内停留超过 3 秒的内容，才写入 24h 滑窗。这样刷到一半刷新页面，不会把自己还没看过的卡片全折叠掉。
   - 命中 24h 滑窗的同质化热点默认**折叠归组**（提示“同类热点已看过”），不直接打入永久黑名单。

#### L3：按需触发的深度评估（仅限详情页 / 当前播放态）
为了避免在列表页拖慢性能或误伤泛娱乐内容（Vlog、音乐、搞笑、游戏实况天然实体密度极低），以下重计算能力**仅在详情页或当前播放单视频时异步触发**：
* **长文本信息熵（压缩率）**：仅当正文或已加载字幕长度 **> 200 字** 时计算压缩比，识别车轱辘话水文。
* **播放态音频特征（Phase 3）**：针对抖音全屏流里把罐头 BGM 混剪成“作者原声”的情况，通过 `chrome.tabCapture` 截取前 3 秒音频计算音频指纹（Chromaprint），绕开网页 `<video>` 的 CORS 限制。

### 3.3 宠物交互与三端差异化渲染

不同平台的网页布局原理完全不同，不能套用同一种遮罩交互：

| 平台 | 页面布局特征 | 命中拦截后的交互策略 |
| :--- | :--- | :--- |
| **B 站网页版** | 规整网格卡片（Grid） | 保持原卡片外框占位，内部替换为半透明宠物占位层（“宠物吃掉了一条低质内容 [吐出]”），防止虚拟列表跳动。 |
| **小红书网页版** | JS 绝对定位瀑布流（`translate3d`） | **严禁改变卡片高度**（否则会破坏 Masonry 坐标计算导致大片留白）。在原卡片内部覆盖等宽高的毛玻璃遮罩，保留右上角“吐出”按钮。 |
| **抖音网页版** | 全屏单视频上下切换（`xgplayer`） | **不能替换成占位条**（会变黑洞且后台继续出声）。命中后立刻静音，弹出半透明宠物浮层倒计时 `1.5s` 自动切下一条（点击可取消）。 |

**投喂与作者拉黑解耦**：
* 点击卡片右上角“投喂”按钮时，**默认只吃掉这条内容特征，不自动永久拉黑作者**（避免正常 UP 主发一条恰饭软广就被永久封杀）。
* 投喂后在屏幕底部弹出 **4 秒撤销条（Undo Toast）**，防手滑。
* 当同一个作者累计被投喂 ≥ 3 次时，宠物气泡主动询问：“这个 UP 主已经被吃掉 3 次了，要直接拉黑吗？”

## 4. 备选方案与取舍（Alternatives Considered & Trade-offs）

### 取舍 1：为什么 MVP 放弃“本地 Python FastAPI 服务”，改用“纯浏览器 Offscreen + WebGPU”？
* **备选方案 A（原方案）**：浏览器扩展 + 本地打包的 Python FastAPI 服务（PyInstaller / Docker）。
  * *优点*：Python AI 生态完整，未来跑重型大模型（LLM）方便。
  * *致命缺点*：普通用户装个插件只需 3 秒，但要额外下载 300MB+ 的本地服务、解决开机自启、端口冲突、HTTPS 访问 Localhost 的 PNA/CORS 限制，安装转化率会断崖式下跌。
* **最终选择（方案 B）**：纯浏览器扩展，在 MV3 的 **Offscreen Document** 中通过 `Transformers.js`（ONNX Runtime Web，优先 WebGPU，自动回退 WASM）直接跑量化模型，用 `IndexedDB` 存向量。
  * *代价*：首装需后台下载一次约 30～60MB 的量化模型权重；暂不适合直接跑 7B 以上本地 LLM。
  * *保留退路*：推理层抽象为统一 `InferenceProvider` 接口，Phase 3 若需接入 Ollama 或本机重型多模态模型，可无缝切换为可选的 Local Daemon 模式。

### 取舍 2：为什么数据抓取采用“拦截原生 API 为主”，而不是“纯 DOM 选择器刮取”？
* **备选方案**：只用 `MutationObserver` + CSS 选择器（如 `.bili-video-card`、`section.note-item`）从 DOM 提取文本。
  * *缺点*：小红书和抖音大量使用构建期混淆类名，平台一发版插件就挂；且 DOM 里拿不到完整的 `music_id`、原始播放/点赞比、作者 UID 等关键特征。
* **最终选择**：在页面 Main World 轻量 Hook `fetch`/`XHR`，被动读取平台推荐流接口返回的原始 JSON，提取完整元数据缓存到内存 Map，再用极简 DOM 映射把卡片节点与 `item_id` 绑定。DOM 选择器仅作为兜底降级方案。

## 5. 边界条件、故障模式与降级策略

这是决定插件“能不能日常长期用”的关键防线：

1. **WebGPU 不可用或模型加载失败（Fail-Open 降级）**
   - 用户的老旧设备不支持 WebGPU 时，自动回退到 WASM SIMD 模式；如果模型仍在下载、崩溃或单批推理超时（**> 500ms**），引擎执行 **Fail-Open（静默放行）**：L1 规则照常生效，L2 跳过本次判定，绝不阻塞原网页卡片渲染，只在宠物图标角标显示“轻装模式”。
2. **抖音连续自动跳过引发的死循环与风控（熔断机制）**
   - 如果连续 3 条抖音视频都命中拦截并触发自动切下一条，系统强制触发**熔断**：暂停自动切换，保留当前视频静音与跳过按钮，由你手动决定是否继续，防止触发平台异常刷屏风控或陷入无限翻页。
3. **长期运行后的向量库膨胀（“越用越空”问题）**
   - 负样本如果只增不减，几个月后积累上千条向量，高维空间里几乎所有新内容都会撞上某条负样本，导致首页大片空白。
   - **对策**：负样本库设置容量上限（默认 1000 条）与**时间衰减权重**（90 天未命中的旧负样本逐步降权并自动归档）；相似度极高（> 0.92）的同类负样本自动合并为聚类中心，控制向量库规模。
4. **MV3 Service Worker 30 秒休眠与通信中断**
   - Chrome MV3 会在空闲 30 秒后强制回收 Background Service Worker。因此**不依赖长连接状态保存在 SW 内存里**：所有持久化状态进 `IndexedDB`，推理状态托管在 `Offscreen Document`，Content Script 通信采用短消息批处理（Batch RPC），并在连接断开时自动重连。
5. **封面图与音频的跨域（CORS / Tainted Canvas）限制**
   - B 站/小红书/抖音的封面图托管在独立 CDN，直接在页面 `<canvas>` 读取像素会触发跨域污染报错。
   - **对策**：封面图统一由 Background/Offscreen 利用扩展的 `host_permissions` 直接 `fetch` 为 `Blob/ImageBitmap` 后送入视觉模型；播放态音频使用 `chrome.tabCapture` 捕获，不碰页面 `<video>` 元素的跨域限制。
6. **重型 SPA 页面的路由切换与内存泄漏**
   - 三大站均为单页应用（SPA），长时间刷流会产生数千个历史 DOM 节点。
   - **对策**：卡片上的“投喂/吐出”按钮使用**轻量原生 DOM / Web Components + 事件委托**，绝不为每张卡片挂载独立 React Root；同时用 `WeakMap` 绑定 DOM 节点状态，节点被平台虚拟列表卸载时自动 GC 回收。
7. **阈值未经标定风险**
   - `bge-small-zh-v1.5` 的中文短句余弦相似度整体偏高（不相关短句也可能在 `0.55` 左右），文档中**不写死拍脑袋的 0.82/0.84**。Phase 1 必须先采集 100 条真实 B 站首页标题（含同类洗稿与不同质量同主题样本）跑一遍分布，再标定默认阈值并提供滑块微调。

## 6. 安全与隐私边界

* **数据不出本地**：浏览器存储与向量检索全部留在你的设备内，除你主动点击“导入/导出特征包”外，没有任何外发网络请求。
* **最小权限原则**：`host_permissions` 严格限定在目标平台域名（`*.bilibili.com`、`*.xiaohongshu.com`、`*.douyin.com` 及对应图片 CDN），不申请 `<all_urls>` 全局读取权限。
* **未来扩展本地守护进程时的安全底线**（Phase 3 预留）：如果后续支持连接本地 Python/Ollama 服务，本地服务必须只监听 `127.0.0.1`、强制校验 `Origin: chrome-extension://<id>` 并启用本地随机 Token 鉴权，防止任意第三方恶意网页通过 `localhost` 窃取你的偏好画像或向黑名单投毒。

## 7. 技术栈与工程骨架

| 模块 | 选型 | 选型理由 |
| :--- | :--- | :--- |
| **扩展工程框架** | **WXT** + TypeScript + React + Tailwind | 现代 MV3 标准框架，原生支持 HMR 热更新、Offscreen、多浏览器一键打包 |
| **端侧推理引擎** | **Transformers.js (ONNX Runtime Web)** | 浏览器原生跑 WebGPU / WASM，零后端安装门槛 |
| **文本 / 视觉模型** | `bge-small-zh-v1.5` (INT8) / `MobileCLIP` | 中文短文本表征强、体积小（30～60MB），适合端侧批处理 |
| **本地存储** | `IndexedDB`（Dexie.js）+ 内存 `Float32Array` | 万级向量纯内存点积耗时 < 2ms，零外部数据库依赖 |
| **开源参考借鉴** | `SeiKasahara/biliblock`（MIT）、`Bilibili-Gate`（MIT） | 借鉴 Offscreen WebGPU 管线、正负样本主动学习及 B 站接口拦截点（保留原 MIT 版权声明，不复用 GPL 代码） |

## 8. 分阶段里程碑与验收标准

### Phase 1：B 站网页版闭环 MVP（预计 1～2 周）
* **交付物**：
  1. WXT 扩展骨架 + B 站首页/推荐流适配器（API 拦截 + 卡片遮罩）。
  2. Offscreen Document 跑通 `bge-small-zh-v1.5`（WebGPU/WASM 自动回退）+ `IndexedDB` 持久化。
  3. 完整“投喂 → 撤销 → 拦截遮罩 → 吐出写入正样本白库”闭环 + 悬浮宠物基础状态反馈。
* **验收标准**：
  - 使用 100 条真实 B 站标题完成默认相似度阈值标定。
  - 首屏 20 张卡片批处理判定 P95 < 150ms（WebGPU），断网或模型禁用时能静默 Fail-Open 放行。
  - 连续投喂 5 条同类 AI 营销号后，刷新首页可自动拦截同类内容；对误杀的优质同主题视频点一次“吐出”后，同类优质视频不再被误杀。

### Phase 2：小红书 & 抖音适配 + 多模态升级（预计 2～3 周）
* **交付物**：
  1. 小红书瀑布流适配器（等高毛玻璃遮罩，不破坏 Masonry 布局）与抖音全屏流适配器（静音 + 1.5s 倒计时跳过 + 连续 3 次熔断）。
  2. 上线 `music_id` 罐头 BGM 加权规则与 24h“有效已读”滑窗折叠。
  3. 引入封面图轻量视觉向量（MobileCLIP）做图文联合打分；上线宠物拦截统计与垃圾词云面板。
* **验收标准**：
  - 小红书滚动 100 张卡片无排版错位或空白断层；抖音连续命中 3 条能稳定触发熔断且无后台串音。

### Phase 3：生态扩展与长期演进
* **特征包订阅**：支持导入/导出社区共享的“AI 营销号 / 罐头 BGM / 标题模板”轻规则包，加速冷启动。
* **播放态音频指纹**：通过 `tabCapture` 识别混剪导出为“作者原声”的换皮罐头 BGM。
* **出海与正向提纯**：复用适配器架构快速接入 YouTube / X (Twitter)；探索面向高纯度内容的“逆向提纯阅读器”。
